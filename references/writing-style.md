# 中国发明专利 · 行文手法与各部分写法范式

本文件讲"怎么写"——中国发明专利说明书/权利要求书的惯用句式、结构与口吻。例句用**通用占位示例**演示
形式，实际撰写时把"第一处理单元/目标对象/预设阈值"等换成本技术方案的真实要素。目标是让产出读起来像
专利代理人写的正式申请文件。

## 通用口吻
- 用"所述"回指已引入的要素：第一次出现"一缓存队列"，之后一律"所述缓存队列"。
- 用上位、功能性措辞：用"通信通道""存储模块""预设阈值"而非具体品牌/数字（数字留实施例）。
- 客观、陈述、无第一人称（"本发明"除外）；少用形容词，多用"用于…""使得…""从而…"。
- 句子可以长、分号分层；权利要求一项常是"一句话 + 若干分号子句"。

---

## 一、说明书摘要（约 200–300 字，一段）
开头固定"本发明公开了一种……"。一段话讲清：解决什么问题 + 用什么手段 + 达到什么效果。不分点、不放附图标记。

**范式：**
> 本发明公开了一种〔发明名称〕。针对〔现有技术的关键问题，一句话〕，本发明〔核心手段，2–3 个分句串起主
> 流程〕；〔点出最关键的创新机制〕。本发明〔一句话效果/有益结论〕。

## 二、权利要求书
独立权利要求是保护范围的核心，最宽；从属逐层加限定。**所有数值/型号/接口都不写进权利要求**，留给实施例。

### 2.0 用"功能/角色/模式"抽象，求宽保护（核心手法）
能用**功能或角色**描述的技术特征，就不要用**具体产品/型号/实现**描述——后者把保护范围钉死在某一种实现上，
别人换个等效实现就绕开了。把"做什么、起什么作用"写进权利要求，把"用什么做的"留给实施例。
- 反例（过窄，绑死具体实现）：`用〔某具体型号部件〕对〔对象〕做〔处理〕`。
- 正例（按功能抽象，覆盖多种实现）：`以〔第一处理单元〕对〔对象〕执行〔某功能〕，输出〔结果〕`；
  若一个特征可由多种形态实现，**再补一条从属权利要求兜住它们**：
  `所述〔第一处理单元〕与〔第二处理单元〕，由同一装置以不同工作模式承载，或分别由不同装置承载。`
- 边界把握：抽象要"宽而仍清楚"——读者能据说明书理解其含义且实施例有支撑；不可宽到含义不清（会因"得不到说明书支持/不清楚"被驳）。凡权利要求里宽出去的写法，说明书必须给出泛化依据（如上面的兜底从属项）。

### 2.1 独立方法权利要求（claim 1）
固定骨架："1.一种〔名称〕，其特征在于，包括以下步骤：" + 步骤 S1…Sn。把**最硬的创新点写进 claim 1 的步骤里**，
不要藏到从属。步骤数 4–7 个为宜，每步一句、分号结尾、末步句号。

**范式：**
> 1.一种〔名称〕，其特征在于，包括以下步骤：
> 步骤S1：〔获取/接入……〕；
> 步骤S2：〔关键处理一，含创新点〕；
> 步骤S3：〔关键处理二〕；
> 步骤S4：〔输出/决策……〕。

### 2.2 从属权利要求
固定开头"N.根据权利要求M所述的方法，其特征在于，〔对某步骤的细化〕："。可对某步展开为若干分句，或给出
可选实现。把"换序校验、阈值闸门、几何反算、状态机、容错重试"等具体机制放这里（仍用上位词，不写死数值）。

**默认相互独立（重要）**：权 2–权 k **默认各自仅从属独立权利要求**（通常为权1），彼此不串联成链；
除非用户明确要求「链式从属」（权3 从属权2 等）。多引从属（「根据权利要求1至N任一项」）按需保留。

**从权去重**：从属不要与独权步骤中的公式/手段句**简单重复**；应保护「难绕过咬合」（约束、互斥、回馈、
校验闭环、状态优先级等）。说明书发明内容新增某步公式时，检查对应从权是否已写过同一手段句，避免三处同义堆砌。

**范式：**
> 3.根据权利要求1所述的方法，其特征在于，步骤S2中所述〔X〕具体包括：
> 〔分句一〕；
> 〔分句二〕。

### 2.3 多引用从属（覆盖式）
> 8.根据权利要求1至7任一项所述的方法，其特征在于，〔一条贯穿性限定，如"全程以唯一标识为键…"〕。

### 2.4 系统/装置权利要求（独立）
固定"一种〔名称〕系统，用于执行如权利要求1至N任一项所述的方法，其特征在于，包括：" + 各"模块"。
每个模块写"X模块，用于〔职责，对应方法某步〕；"。模块应与方法步骤一一呼应。

### 2.5 系统从属（部署/硬件）
> 10.根据权利要求9所述的系统，其特征在于，所述〔A模块〕部署于〔…〕；所述〔B模块〕部署于〔…〕。

> 编号连续；从属正确引用父项；方法权利要求与系统权利要求要素互相对应。常见配比：1 独立方法 + 6~7 从属
> （末条多引）+ 1 独立系统 + 1 系统从属，共约 10 条。

## 三、说明书各部分

### 3.1 技术领域（1 句）
> 本发明涉及〔大领域〕及〔具体子领域〕技术领域，具体地涉及一种〔发明名称〕。

### 3.2 背景技术（"现状—缺陷—收束"三段式）
- 先讲现状/已有方案（可分"第一类…第二类…"）。
- 逐一点出每类的**核心缺陷**，尤其钉死现有技术**「缺哪段闭环」**（缺约束、缺互斥、缺回馈、缺校验、
  缺失败分支等结构性缺口），这是反衬本发明的支点；缺陷用手段级表述，少用空洞形容词。
- 固定收束句："因此，如何〔正面表述要解决的问题〕，是当前亟待解决的技术问题。"
- 配套可写 `现有技术检索纪要.md`：**禁止编造专利号与假百分比**；差异化用可核验的公开系统/文献名与结构性对比。

> 把本发明最强的两个新颖点，在背景里写成"现有技术做不到的痛点"，效果最好。

### 3.3 发明内容（复述 + "进一步地"）
- 先"为克服上述问题与缺陷，本发明提出了一种〔名称〕，包括以下步骤："+ 完整复述 claim 1 的 S1…Sn。
- 再对每条从属，用"进一步地，……"起句复述其限定（基本等于把从属改写成陈述句）。
- 最后"本发明还提出一种用于执行上述方法的系统，包括〔各模块罗列〕。"
- **反组合因果锁专段**（建议）：用一两段写清「为何不是公开模块的随意拼接」——步骤因果顺序、统一状态源、
  互斥/回馈如何咬合；禁止步骤倒挂（后步结果写成前步输入却与独权打架）。
- **步骤衔接与边界**：候选集/近邻集为空、可行域为空、校验失败等边界，必须写清与下一步关系
  （不进入 / 降级 / 整批复核 / 阻断等），并与附图分支一致。
- **失败/降级状态机**：状态名互斥、进出条件完整；改名须全文替换。可与从属中的状态优先级条款咬合。
> 这一节几乎是权利要求的镜像，**术语必须与权利要求逐字一致**。

### 3.4 有益效果（每个好处一段，"本发明……"起句）
逐条对应创新点，**以手段领头讲因果**（先写做了什么，再写得到什么），避免堆无因果的形容词或无关热点。范式：
> 本发明〔采用/通过 某机制〕，〔解决了/克服了 某问题〕，〔带来 某效果〕。
可辅以反事实一句（若去掉该咬合，公开拼盘仍无法达到…），但勿编造量化指标。

### 3.5 附图说明（每图一句）
固定句式：
> 图N为本发明实施例〔提供的/中……的〕〔图的内容〕示意图；
（最后一图用"……框图。"或"……示例。"）

### 3.6 具体实施方式
> 实施例的**数量、类型与顺序由本技术方案决定**——下面列的"方法/系统/示例"是常见组合，不是必须三个、
> 也不是固定模板。引用附图时图号按你实际的附图编排来写（不要照搬"图5是架构图、图3图4是JSON"这类范文固定法）。
- 起头两句固定：
  > 下面结合具体的实施例对本申请进行说明：
  > 为了让本领域的技术人员更好地理解本发明的技术方案，下面将结合附图和具体实施例对本发明进行详细的阐述。
- **实施例1（方法）**：开头"本实施例主要描述一种〔名称〕。参见图〔对应流程图图号〕……，该方法……。具体步骤
  详述如下："。然后**每个步骤两段**：先复述该步（"步骤S1：……。"，与权利要求一致），再"在本步骤中，……"
  详解——这里**大量使用"例如""优选""如"引出真实参数/型号/接口/数值**（如毫秒级、阈值0.90、某商用模型…，
  须与真实方案一致）。这是把"宽泛权利要求"落到"可实施细节"的地方。
- **实施例（系统）**（若有系统权利要求）：开头"参见图〔对应架构框图图号〕，本实施例介绍一种……系统，用于
  执行……所述的方法。……主要包括以下模块。" 然后逐模块一段；末段讲部署/并发/连接关系/硬件型号举例。
- **实施例（结构化输出/正反例）**（**仅当本发明确有结构化输出且值得展示判别逻辑时才写**）：结合相应附图展示
  系统输出的 JSON/报文等。分"场景一：……（正例）"与"场景二：……（反例）"两个小标题段 + 详解段，正反对照
  说明判别逻辑。**示例数据必须自洽、且服从说明书里定义的规则**（如分级规则、字段语义），不得自相矛盾。
- 结尾固定收束句：
  > 本说明书中各个实施例采用递进的方式描述，每个实施例重点说明的都是与其他实施例的不同之处，各个实施例之间
  > 相同相似的部分互相参见即可。

**实施例两段式示例（演示形式）：**
> 步骤S2：对所述数据进行特征提取，得到特征表示。
> 在本步骤中，系统优选采用〔某类模型，例如某商用模型 X〕对输入进行处理，在毫秒级时间内输出〔…〕。为提升
> 〔某指标〕，本实施例进一步设置〔预设阈值，例如 0.90〕：当〔条件〕时……；否则……。

## 四、自查清单（写完通读一遍）
- [ ] claim 1 含最硬创新点；从属逐层细化且引用正确；系统权利要求与方法步骤呼应。
- [ ] **从属默认仅从属独权、相互独立**（除非用户要求链式）；从权未简单重复独权手段句。
- [ ] 权利要求**无**具体数值/型号/接口；这些只在实施例以"例如/优选"出现。
- [ ] 发明内容与权利要求**术语逐字一致**；有益效果以手段领头、逐条对应创新点。
- [ ] **权利要求1 步骤原文**与发明内容步骤段、实施例开篇步骤段为**同一字符串源**（或逐字镜像），禁止三处各写一版导致漂移。
- [ ] 从属权利要求 ↔ 发明内容「进一步地…」↔ 实施例细化，三处要素对齐。
- [ ] 背景钉住「缺哪段闭环」；有反组合因果锁；步骤无倒挂；边界分支与下一步关系写清。
- [ ] 失败/降级状态机互斥完整；不堆无关热点凑新。
- [ ] 附图说明每图一句、句式统一；图号与实施例引用一致；图内无「图N 标题」。
- [ ] 实施例步骤复述行与权利要求一致；"在本步骤中…"详解充分、含真实可实施细节。
- [ ] 全篇"所述"回指规范；无第一人称；收束句到位。
- [ ] **通用英文缩写**：首次「中文全称（英文）」，后文可只用英文（如 ROI / IoU / NPU）；勿全文堆中文全称或突然冒出未定义缩写。
- [ ] **图中/图注里的英文缩写**在正文或附图说明**首次出现处给出中文全称**，勿让图引入正文未定义的缩写。
- [ ] 若有 OMML 公式：符号表与式(n)同形；有等式本体；渲染后角标可见、无 ❑（见 `references/omml-equations.md`）。
- [ ] 附图纯黑白（无彩色填充）；边不交叉穿框；装配后整篇 soffice 渲染逐页看过。
- [ ] **去 AI 味（背景/有益效果）**：无堆叠「首先/其次/另外/此外/因此/从而/随着…发展」；长逗号链已断句为句号；总起句有明确主语（非空编号壳）。
- [ ] **空口号落地**：无「填补空白/具有重要意义/越来越好」等空话；价值写成手段→效果因果。
- [ ] **对标式客观**：背景/对比写「相同印证 + 差异剖析原因」，不抬高不盲从；适用边界用实施例「优选/例如」范围表达，非论文式局限致歉。
- [ ] **本地改写**：权要/说明书未上传云端 AIGC/查重站；未对权利要求做多语种翻译链改写。
- [ ] 建议交付：HANDOFF、踩坑要点、检索纪要、权要走读、代理人抽查、质量/创新性报告（按需）。

## 五、反面清单（真实踩过的坑，提交前逐条排查）
- **照搬模板/范文的技术内容**（这是最严重的错）：模板只提供**格式、行文、版式**；技术方案、架构、层级、
  模块名、步骤划分、图的数量与种类，**一律据用户的真实材料/代码生成**。绝不把范文里的具体技术（某种特定的
  级联结构、特定模型分工、特定字段/JSON 等）搬进新专利——换个用户就是另一套技术，搬过去既错又涉抄袭。
- **正文混入起草思考前言/旁注**（"Let me…""The advisor…""补充说明（非正文）…"等）→ 提交前全文检索英文
  句与"说明:/补充说明/交付物"并清零。这类草稿痕迹最容易在分段起草时漏到正文里。
- **实施例步骤编号与权利要求不一致**（实施例自造 `S2-1`，而权利要求是 S1–S4）→ 实施例步骤必须落实权利要求
  的同一套步骤划分，编号对齐。
- **权利要求 / 发明内容「进一步地」/ 实施例 各写各的** → 术语与步骤漂移；应用单一 `CLAIM1_STEPS`（或等价）源字符串生成三处。
- **示例自相矛盾 / 违反自定义规则**（如某记录的状态字段与其结论打架；或把本应被排除的样例又写成生成了上报；
  或样例的分级违反说明书自己写的分级规则）→ 正反例的字段、数值、结论必须自洽，且服从说明书定义的规则。
- **半角标点**混入中文正文 → 归一为全角（技术记号 `x1,y1`/`0.55` 与 JSON 代码块除外）。中文叙述里避免用 `/` 连接并列（用「与」「及」）。
- **段落过长**（动辄上千字一段）→ 按句拆成贴近模板段长的短段。
- **凭空捏造数值/机制** → 一律以代码或交底材料为准，不确定就问用户，不杜撰。
- **OMML 上下角标渲染为空方框 ❑**：`m:sub`/`m:sup` 内多包了 `m:e`；或 nary 留了空限节点；或只用 XML 计数未做 PDF 渲染校验。见 `references/omml-equations.md`。
- **附图带彩色/浅色填充**：CNIPA 附图惯例白底纯黑；手搓或旧脚本出的彩图必须重画为 `vflow`/`vmodules` 纯黑白后再嵌。
- **只靠结构审计 PASS 就交付**：`oMath` 个数对、段落数对 ≠ 角标可见、页眉正确、图未截断。必须第 7 步逐页渲染。
- **手改终稿 docx 当真源**：下次 rebuild 冲掉；只改 content/figure/assemble 源；覆盖前 bak；初稿永不覆盖。
- **悬空式号 / 一名多义 / 旧变量回潮**：式(n)无等式本体；同一符号多义；已废弃决策变量又写回正文。
- **从属误串联或与独权复读**：权2–k 默认可各自从权1；从权应加固咬合而非复读独权公式句。
- **拼盘答辩脆弱**：无反组合因果锁；检索纪要假专利号/假%；堆联邦/大模型/跨链等无关热点凑新。
- **状态机残缺 / 边界未衔接**：失败降级无互斥；候选为空未说明是否进入下一步。
- **图内图号标题 / 边交叉穿框**：标题只在附图说明；交叉顶绕；改图不 rebuild。
- **聊天外泄权要与说明书正文**：用户要求时只报结构结论与验收，正文留本地。
- **AI 连接词堆叠 / 逗号长链**：背景技术、有益效果里「首先/其次/另外/此外/因此/从而/随着…发展」连环出现，或一逗到底的 AI 上句——删特征连接、拆成句号；**保留**专利惯用「进一步地/所述/用于」。
- **空编号总结壳 / 无主语总起**：`(1)…(2)…` 僵硬壳或总起句缺主语——改为有主语的陈述段。
- **空口号与夸张修饰**：「填补空白」「具有重要意义」「越来越好」及夸张形容词——改写为手段→效果；可选反向润色时只升动词/严谨度、技术内容不动。
- **把专利写成论文 Discussion / 口语人情味**：禁论文式局限致歉、禁口语感情句；适用边界写在实施例优选范围。
- **权要上传云端检测 / 多语种翻译链改权利要求**：泄露风险 + 破坏三处同源与权要一致性；只本地改写；非权要叙述若试用翻译链须人工回校且标注风险。

## 六、去 AI 味与对标式行文（不改版式）

本节目的：降低说明书叙述中的模板化「AI 味」，并对标优质专利的**逻辑**写背景与对比——**不改变** docx 版式、分节、附图、OMML、装配脚本或权利要求的法律骨架。既有红线（只借格式不抄内容、权要宽泛、三处同源、OMML、附图纯黑等）一律不削弱。

### 6.1 砍 AI 特征连接与逗号长链（尤适用于背景技术 / 有益效果）
- **删除或改写**堆叠的：首先 / 其次 / 另外 / 此外 / 因此 / 从而 / 随着…发展（及近义空转连接）。
- **保留**专利惯用语：进一步地 / 所述 / 用于 / 其特征在于 等（这些不是「AI 味」要砍的对象）。
- 把 AI 式「一逗到底」的长上句拆成**句号**短句，切断假逻辑链；**权利要求**仍可用分号分层，本条主要针对说明书叙述段。

### 6.2 避免空壳编号总结；总起句必有主语
- 不要用僵硬的 `(1) … (2) …` 空总结壳堆砌「意义/价值」。
- 每一段总起句须有**清晰主语**（本发明 / 所述方法 / 现有方案甲…），禁止无主语句号碎片。

### 6.3 实施例继续补干货（强化既有要求）
- 实施例「在本步骤中…」须落到**具体参数、步骤细节、场景/优选范围**；忌纯概括套话。
- 可选写清**适用边界**（如优选阈值区间、适用工况），用「例如/优选」表达——**不是**论文式「本研究的局限性」致歉段。

### 6.4 精选同义替换（专利可用）
| 宜少用 / AI 高频 | 专利向替换或写法 |
|------------------|------------------|
| 完善 | 优化 / 改进 |
| 推动 | 促进 / 推进 |
| 通常情况下 / 一般而言 | 在多数情形下 |
| 填补空白 / 具有重要意义 / 越来越好 | 改写为**手段→效果**因果（做了什么 → 得到什么），勿空喊 |
| 随着 X 的发展，Y 越来越好 | 在 X 过程中，Y 在…方面得到改进 |
| 因此 / 从而（空转衔接） | 直接陈述因果：通过… / 采用…后…；或拆句省去连接词 |

有益效果继续遵守「效果手段领头」：先手段后效果，不堆无因果形容词。

### 6.5 可选：反向润色（技术内容固定）
- 在**严丝合缝保留**技术方案、步骤、符号与三处同源用词的前提下，只升级动词与表述严谨度。
- 删除夸张修饰语；**禁止**为「降 AI」而改权利要求步骤原文或打乱术语表。

### 6.6 对标优质专利：只学逻辑，不学文字
- 读模板/对标专利时：**学结构与论证逻辑**（现状—缺陷闭环—手段—效果），**不照搬文字与技术内容**（与「只借格式不抄内容」一致）。
- **现有技术对比**：相同点相互印证；差异点剖析原因；客观，不抬高本发明、不盲从前案。
- 价值表述落地为**手段→效果**，禁止空口号。

### 6.7 完稿自检身份与本地安全
- 草稿完成后，以**资深专利代理人**视角通读：权要可实施、支持充分、术语一致、无空转连接与空口号。
- **仅本地**改写与核验；**禁止**将权利要求/说明书正文上传云端 AIGC 检测站或在线查重站（与技能「安全/协作、不外泄正文」一致）。
- **默认不对权利要求做多语种翻译链**（中→英→俄/法→中）——易破坏权要表述一致性与三处同源；若对非权要叙述段试用，须人工回校，并清醒知悉风险。

### 6.8 专利场景明确不做（防误吸论文技巧）
- 不做 Paperpass/知网等挂网查重流程教程式默认步骤。
- 不引入投稿选刊、Sci-Hub、口语人情味、夸张感情句。
- 不把说明书写成论文 Discussion；不把「局限」写成学术致歉。
- 不削弱既有红线，不改版式/脚本/模板。
